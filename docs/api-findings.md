### `DATE` 요청 인자: 진행 중 필터로 쓸 수 없음

`culturalEventInfo`는 선택 요청 인자 `CODENAME` / `TITLE` / `DATE`를 받습니다.
`DATE`는 동작하지만 **`STRTDATE` 또는 `END_DATE`와 문자열 앞부분이 일치하는 행만** 거릅니다.

| 요청 | 결과 |
|---|---|
| 없음 | 19,486 |
| `DATE=2026-08-13` | **12** — 시작일이 08-13이거나 종료일이 08-13인 행만 |
| `DATE=2026-08` | 353 — 8월에 시작하거나 8월에 끝나는 행만 |
| `CODENAME=전시/미술` | 326 |

**"그날 진행 중"이 아닙니다.** 2026-W33에 실제로 겹치는 행사는 295건인데
`DATE=2026-08-13`은 12건만 줍니다. `07-01~09-30` 같은 장기 행사는
`DATE=2026-08`에도 잡히지 않습니다.

→ **조회 단계 날짜 필터는 포기하고 전량(20요청·약 10초) 수집 후 코드에서 거릅니다.**

### ⚠️ 레이트 리밋이 500으로 위장돼 나온다 (가장 중요한 발견)

비짓서울은 호출이 잦으면 **429가 아니라 500 Internal Server Error**를 돌려줍니다.
특정 `cid`나 카테고리의 문제가 아닙니다 — 실패한 `cid`를 간격을 벌려 다시 부르면 전부 200입니다.

같은 6건을 간격만 바꿔가며 호출한 결과:

| 호출 간격 | 성공률 |
|---|---|
| 120ms | 3/6 (50%) |
| 400ms | 4/6 (67%) |
| 1000ms | 6/6 (100%) |

`POST /contents/list`의 카테고리 필터도 같은 이유로 약 30% 실패합니다.

**계획의 "상세 한 건 실패는 건너뛴다"가 위험합니다.** 120ms 간격으로 156건을 hydrate했을 때
**94건(60%)이 조용히 사라졌습니다.** 로그에 경고만 찍히고 배치는 성공한 것처럼 끝납니다.

→ Task 6에 세 가지를 넣었습니다:
1. 목록·상세 **모두** 250ms×시도횟수 백오프로 4회까지 재시도
2. `DETAIL_DELAY_MS`를 120 → **400**
3. **유실률 가드** — 캐시 폴백도 없이 사라진 항목이 10%를 넘으면 배치를 깨뜨린다

기준을 "호출 실패율"이 아니라 **"유실률"**로 잡은 이유: 캐시 구본으로 메운 실패는 손실이 아니고,
정상 상태(대부분 캐시 적중)에서 호출 실패율로 재면 한 건만 실패해도 100%가 되어 오탐합니다.

적용 후 같은 156건 재실행: **상세 호출 156건 / 실패 0건 / 유실 0건.**

### 영업시간 파싱 성공률 (스펙 14장 #6)

역사(88) + 자연(68) 카테고리 156건 표본 — place 155건 중 `cmmn_use_time`이 있는 것 116건:

**파싱 성공 63건 = 54%**

실패 원문에서 반복되는 패턴:

| 패턴 | 예시 | 처리 가능한가 |
|---|---|---|
| 상시 개방 | `24시간`, `24시간 개방`, `상시개방` | ✅ 규칙 추가로 가능. **가장 흔함** |
| 자연광 기준 | `일출 시 ~ 일몰 시` | ⚠️ 고정 시각이 아니라 표현 불가 |
| 위임형 | `업체별 상이`, `층별로 상이`, `카페는 별도 확인 필요` | ❌ 애초에 단일 시간대가 없음 |
| 조건부 | `법회, 기도 불공 등 사찰 일정에 따라 차이가 있음` | ❌ 파싱 대상이 아님 |

**`24시간` / `상시개방` 계열을 `00:00~24:00`으로 읽는 규칙을 넣었습니다 → 성공률 54% → 86%**
(116건 중 100건, 그중 40건이 이 규칙으로 잡힘).

`연중무휴`는 이 규칙에 넣지 않았습니다. 쉬는 날이 없다는 뜻이지 24시간이라는 뜻이 아닙니다
(`연중무휴 10:00~18:00`이 흔합니다).

남은 16건은 규칙을 더 넣어도 이득이 없습니다 — 애초에 단일 시간대가 없는 원문들입니다:
`일출 시 ~ 일몰 시`, `업체별 상이`, `층별로 상이`, `캠핑장 입실 13:00 ~ 퇴실 익일 11:00`,
`법회 일정에 따라 차이가 있음`. 스펙의 best-effort 원칙대로 `null` + 원문 노출로 둡니다.

서울시 275 / 비짓서울 39로 갈린다.

AGENTS.md의 "두 소스는 대칭이다"가 데이터로 확인됐다. 서로 다른 것을 담고 있다.

이벤트 314건 **전부 좌표와 이미지가 있다.** 근처 화면과 카드 UI가 빈 곳 없이 채워진다.

### 실행 중 드러난 결함 3개

1. **ECONNRESET에 배치 전체가 죽었다.** `postWithRetry`가 HTTP 상태만 재시도하고
   `fetch`가 던지는 예외는 놓쳤다. 2,199건을 도는 동안 커넥션 리셋 한 번이면 끝이다.
   → 예외도 재시도. 목록은 위로 던지고, 상세는 그 건만 실패로 센다.

2. **캐시를 emit에서만 저장해 20분치가 날아갔다.** 초회 hydrate가 40분 넘게 걸리는데
   마지막에만 저장하면 그 사이 어떤 실패에도 전부 잃는다.
   → CLI가 30초마다 스냅샷을 뜨고, 실패해도 받아둔 만큼 남긴다.

3. **Ollama가 `UND_ERR_HEADERS_TIMEOUT`으로 죽어 규칙 폴백으로 넘어갔다.**
   `stream:false`면 생성이 끝나야 헤더가 오는데, undici 기본 headersTimeout이 300초다.
   실측 생성 224초 + 모델 로딩 40초라 **정상 경로에서 매번 터진다** —
   하루 한 번 도는 배치는 모델이 항상 언로드 상태이기 때문이다.
   → `stream:true`로 바꿔 헤더를 즉시 받는다. 조각을 이어붙여 파싱한다.
   콜드 스타트에서 2분 17초에 완주 확인.

폴백은 설계대로 동작했다(`providerName: 'rule (ollama 실패)'`, 12건 유지). 화면은 비지 않았다.

### 캐시 슬림화 (2026-08-14)

`post_desc`는 **행사·장소 소개 본문**이다. `sumry`가 한 줄 요약이면 이쪽은 전체 설명글이고,
2,199건 중 2,134건에 100자 이상 실질 본문이 있다. 버릴 내용이 아니다.

문제는 껍데기였다 — 네이버 스마트에디터 boilerplate CSS가 항목마다 1.5KB씩,
본문에 base64 이미지가 통째로 박힌 항목도 있었다(raw 2.0MB인데 본문은 548자).

**HTML을 걷어내고 텍스트만 남긴다: 17.4 MB → 7.5 MB (57% 감소).**
**적용 완료** — 구현은 `src/lib/html.ts`의 `htmlToText`이고, `src/sources/visit-seoul.ts`의 `slimDetail`이 `post_desc`에 적용한다.
제품에서 외부 HTML을 렌더링할 일이 없으므로 XSS·스타일 오염 위험만 덜어낸 셈이다.

태그 정규식은 속성값을 따옴표째 건너뛴다. `<[^>]*>`로 잡으면
`data-sheets-value="{"a":1}"` 같은 속성에서 일찍 끊겨 JSON이 본문으로 샌다(실측 5건).
