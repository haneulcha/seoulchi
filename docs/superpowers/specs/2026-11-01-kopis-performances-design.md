# 공연 소스(KOPIS)와 위치 기반 추천 선반 설계 (2026-11-01)

KOPIS(공연예술통합전산망) 공연 데이터를 세 번째 소스로 붙이고, 홈의 추천 선반을
주간 큐레이션에서 **사용자 위치 기준 규칙 선반**으로 바꾼다.

이 문서는 `2026-10-26-today-home-design.md`(오늘 중심 홈)의 추천 선반 부분을 고쳐 쓴다.
나머지 홈 구조(날짜 탭, 목적 칩, 내 주변 기본, 자치구, 페이지네이션)는 그대로다.

## 1. 왜

사용자 관찰: 공공 데이터 행사가 많아서 재미 요소가 덜하다. 더 흥미로운 데이터가 필요하다.
조사 끝에 공연(KOPIS)과 팝업을 후보로 봤고, 팝업은 공식 API가 없고 약관상 사전 동의가 필요해
이번 범위에서 뺀다. 공연은 공식 API이고 무료이며 이용 범위 제한이 없다(공공데이터포털 표기).

공연을 어떤 순간에 쓰는가 (사용자 답):

- **즉흥적으로 보는 순간이다.** 기대작은 미리 예매한다. 이 앱은 "오늘 뭐 볼까"의 순간이다.
- 그 순간을 막는 것은 **가격**이다. 즉흥적으로 보려는데 너무 비싸면 부담이 된다. 무료면 가장 좋다.
- **집 근처**여야 한다.
- 장르는 개인 취향이라 앱이 기준을 세울 수 없다.
- **동네 공연이 흥미롭다.** 먼 세계 사람이 아니라 내 주변 이웃이 출연하거나 기획한 공연이라서다.

## 2. 결정

| 항목 | 결정 | 누가 |
|---|---|---|
| 소스 | KOPIS를 세 번째 소스로 추가한다 | 사용자 |
| 팝업 | 이번 범위 밖 | 사용자(조사 후 공연 먼저 진행) |
| 예매 순위(boxoffice) | 쓰지 않는다. 미리 예매하는 대형 공연이 채우는 목록이라 즉흥 관람과 반대다 | 제안, 사용자 이의 없음 |
| 목록에서 공연 | 다른 행사와 **똑같이** 섞어 보여준다. 가격 필터나 강조를 따로 두지 않는다 | 사용자("그냥 동일하게 보여줘") |
| 상세 호출 | 가격·시간 때문에 상세를 쓴다. 처음에 천천히 전부 받고, 이후엔 바뀐 것만 받는다 | 사용자 승인("그렇게 하자") |
| 추천 선반 | **사용자 위치에 따라 달라진다** | 사용자 |
| 선반의 성격 | "누가 골라 준 것"에서 "가까이에서 싸게 볼 수 있는 것"으로 바뀌어도 된다 | 사용자("바뀌어도 돼") |
| 선반 규칙 대상 | 공연만이 아니라 **모든 행사**에 같은 규칙 | 내 판단 — 한 홈에 기준이 둘이 되지 않게 |
| 요청 검사 | 만들지 않는다. 응답 검사와 픽스처 테스트만 둔다(6장) | 합의 |

## 3. 실측 (2026-10-31, 서울)

필드명과 호출 규약의 근거는 실측이다. 구현 전에 `docs/api-findings.md`에 KOPIS 절로 옮긴다.
공식 스펙: <https://kopis.or.kr/por/cs/openapi/openApiList.do?menuId=MNU_00074>,
개발 가이드 PDF v5.0(2026-04-23, 같은 페이지 링크).

**엔드포인트** (`https://kopis.or.kr/openApi/restful/…`, 응답은 XML만)

| 용도 | 경로 | 묶음 | 핵심 필드 |
|---|---|---|---|
| 공연 목록 | `pblprfr?stdate&eddate&cpage&rows&signgucode=11` | 100건/쪽 | `mt20id prfnm prfpdfrom prfpdto fcltynm poster genrenm openrun prfstate` |
| 공연 상세 | `pblprfr/{mt20id}` | 1건 | `pcseguidance`(요금 원문) `dtguidance`(시간 원문) `mt10id`(시설) `relates/relate/relateurl`(예매) `entrpsnm*`(기획·제작) `updatedate` `prfruntime` `prfage` |
| 시설 목록 | `prfplc?cpage&rows&signgucode=11` | 100건/쪽 | `mt10id fcltynm fcltychartr`(시설특성) `gugunnm`(구) |
| 시설 상세 | `prfplc/{mt10id}` | 1건 | `la lo`(좌표) `adres` |

- 목록에는 가격·시간·좌표·구가 없다. 가격·시간은 공연 상세, 좌표는 시설 상세에만 있다.
- 목록과 시설 목록에 `afterdate=YYYYMMDD`(그날 이후 등록·수정분만)가 있다.
- 조회 기간은 최대 31일, 쪽당 최대 100건(결과 코드 05, 06).
- 날짜 형식: 요청은 `YYYYMMDD`, 응답은 `YYYY.MM.DD`.

**규모.** 오늘 공연 중 297건(연극 129, 뮤지컬 68, 대중음악 38, 클래식 36, 국악 9, 복합 7, 무용 5, 서커스·마술 5),
오픈런 73. 서울 시설 1,784곳.

**가격.** 무작위 40건의 요금 원문에서 "숫자+원" 최솟값을 뽑는 규칙으로 40/40 읽혔다.
무료 1, 2만 원 이하 9, 2~4만 원 8, 4만 원 초과 22. 싼 공연은 단발 소규모 공연·정기연주회·국악원 쪽에 몰렸고,
대학로 장기 공연은 대부분 4~6.6만 원이었다. 조건부 최저가가 있다("현장판매 15,000원, 사전예약 10,000원", "마티네석 10,000원").

**시설 유형과 지역.** 297건을 시설 이름으로 시설에 잇자 전부 이어졌다(이름 앞부분 일치라 일부 오매칭 가능).
대학로 민간 129 / 대학로 외 민간 96 / 공공(기타) 24 / 국립 20 / 비공연장 16 / 공공(문예회관) 12.
구별로 종로구 145(절반), 서초 26, 마포 23 … 강서 2, 은평·관악·양천·금천·중랑 각 1.

**동네 공연 신호는 시끄럽다.** 공공 시설 36건에는 구로 클래식 페스타 비바체 합창단, 강북 대방놀이판,
종로 가족공연축제, 동대문문화재단 기획공연이 있지만 올림픽공원 아이돌 콘서트와 대형 뮤지컬도 섞여 있다.

**기존 데이터와 겹침.** 동네 공연으로 보이는 13건 중 3건(서리풀 재즈페스타, 숨비소리, 연희판판)이
이미 서울시 데이터에 있다. 제목 표기가 다르다
(`[서초문화재단] 2026 서울어텀페스타 선정작 [숨비소리, 해녀들의 노래]` 대 `숨비소리, 해녀들의 노래`).

**호출 제한(문서에 없음).** 상세를 연달아 약 20건 부르자 사이트 방화벽이 HTTP 400 HTML
"Request Blocked"를 돌려줬다. API의 XML 오류가 아니다. 1.5초 간격에서도 8건 뒤 다시 막혔고,
몇 분 뒤 풀렸다. 시설 목록은 3초 간격 18쪽을 막힘 없이 받았다. 기준값은 모른다.

**결과 코드.** 오류도 HTTP 200이다. 정상 응답에는 `returncode`가 없고, 오류는
`<db><returncode>NN</returncode><errmsg>…</errmsg></db>`. 00 정상, 01 파라미터 오류, 02 키 미등록,
03 DB 오류, 04 데이터 없음, 05 기간 31일 초과, 06 100건 초과.

**확인하지 못한 것.** 하루 호출 한도, 차단 기준과 해제 시간, 포스터 이용 조건,
포스터를 https로 받을 수 있는지(URL이 `http://www.kopis.or.kr/upload/…`).

## 4. 소스: KOPIS

기존 `EventSource` 인터페이스(`src/sources/types.ts`: `fetchList → hydrate → normalize`)에 맞춘다.

**수집 범위.** 카탈로그 지평(오늘부터 8주, `selectCatalog`)을 덮도록 31일 이하 창 여러 개로 목록을 부른다.
`signgucode=11`. 쪽은 받은 건수가 `rows`보다 적을 때까지 넘긴다.

**상세와 시설은 캐시한다.** 초기 적재 한 번 뒤로는 바뀐 것만 부른다.

- 공연 상세 캐시: `mt20id → 상세`. 캐시에 없거나, 마지막 실행일 이후 `afterdate` 목록에 나온 공연만 다시 부른다.
- 시설 캐시: `mt10id → { 좌표, 주소, 시설특성, 구 }`. 시설 목록(묶음)과 시설 상세(좌표, 1건씩)로 채운다. 거의 바뀌지 않는다.
- 캐시는 비짓서울 캐시(`data/cache/visitseoul.json`)처럼 저장소에 커밋되는 파일로 둔다.

**호출 속도와 차단.** 단건 호출은 순차로, 간격을 두고 부른다. 간격은 상수 하나로 두고 3초에서 시작한다.
차단 HTML이 오면 그 실행의 단건 호출을 멈추고, 그때까지 받은 캐시를 저장하고, 상세가 없는 공연은 이번 산출에서 뺀 채
파이프라인을 계속한다. 다음 날 실행이 이어 받는다(초기 적재가 며칠에 걸쳐 수렴해도 된다).
건수(받음·남음·차단 여부)는 stderr와 `meta.json`에 남긴다 — 조용히 줄어들지 않게.

**정규화 (KOPIS → `EventItem`)**

| Item 필드 | 값 |
|---|---|
| `id` | `kp-{mt20id}` (`idSchema` 접두사에 `kp` 추가) |
| `source` | `'kopis'` (`sourceNameSchema`에 추가) |
| `title` | `prfnm` |
| `category` | `genrenm` 원문. `GROUP_BY_RAW`에 KOPIS 장르 8종을 정확 일치로 넣어 전부 **보러 가기** |
| `place` | `fcltynm` |
| `district`, `lat`, `lng`, `address` | 시설 캐시의 `gugunnm`, `la`, `lo`, `adres`. 좌표가 없으면 비운다 |
| `startDate`, `endDate` | `prfpdfrom`, `prfpdto`를 `YYYY-MM-DD`로 |
| `time` | `dtguidance` 원문 (서울시 `PRO_TIME`과 같은 규칙: 파싱하지 않는다) |
| `fee` | `pcseguidance` 원문 |
| `isFree` | 원문에 "무료"가 있고 금액이 없을 때 |
| `imageUrl` | `poster` |
| `linkUrl` | 첫 `relateurl`(예매 링크) |

**선반 규칙이 쓰는 새 필드 둘** (선택 필드, 모든 소스 공통 스키마에 추가)

- `minPrice?: number` — 요금 원문의 "숫자+원" 최솟값. 무료는 0. 못 읽으면 비운다.
  서울시 소스의 `fee` 원문에도 같은 파서를 쓴다(읽히는 만큼만).
- `localVenue?: boolean` — KOPIS 시설특성이 `공공(문예회관)` 또는 `공공(기타)`이면 true.
  실측상 이 신호는 시끄러워서(3장) 선반에서 약하게만 쓴다.

**중복.** 서울시 데이터와 겹치는 공연이 있다. 현재 `mergeItems`의 키(`kind|정규화 제목|정규화 장소`)는
제목 표기 차이 때문에 이 겹침을 놓친다(3장 예). 서울시 소스가 기준(id 생존)이고 KOPIS가 비어 있는 필드를 채우는
기존 우선순위는 유지한다. 겹침을 어떻게 잡을지(예: 기간 겹침 + 좌표 근접 + 제목 포함 관계)는 계획에서 정한다.
`docs/2026-08-22-backend-migration-plan.md`의 동일성 판정 설계와 어긋나지 않게 한다.

**키.** `KOPIS_API_KEY` 환경 변수. 배치 워크플로에 GitHub 시크릿으로 추가한다(사용자가 등록).

## 5. 추천 선반: 위치 기반 규칙

지금은 빌드 때 주간 큐레이션 파일(`data/curated/*.json`)에서 고른 3장이 모두에게 같다.
바뀐 뒤에는 **브라우저가 카탈로그 인덱스에서 3장을 고른다.** 인덱스에는 이미 좌표·무료 여부가 있으므로
빌드 단계에 후보를 따로 굽지 않는다(새 필드 `minPrice`, `localVenue`만 인덱스에 추가).

**후보.** 오늘부터 이번 주말까지 하루라도 갈 수 있는 행사(지금 `pickShelf`의 날짜 조건과 같다).
날짜 탭·목적 칩·자치구 필터와 무관하게 늘 같은 자리다(오늘 홈 설계 2장 유지).

**위치가 있을 때.**
1. 거리순으로 정렬한다.
2. 무료, 2만 원 이하에 가산점을 준다.
3. `localVenue`에 약한 가산점을 준다.
4. 같은 장소에서는 1장만 고른다.
5. 앞에서 3장.

가산점의 세기는 상수로 두고, 실제 화면을 보며 조정한다. 정답을 미리 정하지 않는다.

**위치가 없을 때**(권한 거부, 확인 전, 내 주변 끔). 서울 5개 생활권에서 생활권당 1장씩, 같은 점수 규칙
(거리 항목만 빼고)으로 고른다. 생활권은 고정 표로 둔다.

| 생활권 | 자치구 |
|---|---|
| 도심 | 종로, 중구, 용산 |
| 동북 | 성동, 광진, 동대문, 중랑, 성북, 강북, 도봉, 노원 |
| 서북 | 은평, 서대문, 마포 |
| 서남 | 양천, 강서, 구로, 금천, 영등포, 동작, 관악 |
| 동남 | 서초, 강남, 송파, 강동 |

생활권이 5개이고 선반이 3장이므로 어느 생활권을 고를지는 계획에서 정한다(예: 점수 상위 생활권 3개).

**프리렌더 첫 그림.** 정적 페이지는 위치를 모른다. 첫 그림은 위치 없는 규칙의 결과를 빌드 때 구워 두고,
위치가 확인되면 브라우저에서 다시 고른다. 홈 목록과 같은 위치값(`useGeo`)을 쓰고 권한을 따로 묻지 않는다.

**선반 아래 목록.** 지금처럼 선반에 오른 행사는 목록에서 뺀다.

**카드.** 선반 카드의 코멘트(`reason`)는 규칙 선반에서 쓰지 않는다. 지금도 운영 배치는 빈 문자열이라
화면 차이는 없다.

## 6. 검사

- **응답 검사(필수).** 모든 KOPIS 호출이 하나의 파싱 경계를 지난다. `returncode`가 있으면 코드와 메시지로 던지고,
  04만 빈 결과로 바꾼다. 차단 HTML(XML이 아닌 응답)은 별도 오류로 구분한다(4장 처리). 정상 응답은 zod로 검사해서,
  필드가 바뀌면 빈 데이터 대신 실패한다.
- **픽스처 테스트.** 실측 XML(목록, 상세, 시설 목록, 시설 상세, 오류 01·02, 차단 HTML)을 `tests/` 아래 픽스처로 두고
  파서와 정규화를 고정한다. 키 없이 CI에서 돈다.
- **요청 검사는 두지 않는다.** 틀린 요청은 서버가 01·05·06으로 거절하고, 위 응답 검사가 그것을 실패로 드러낸다.
- **실서버 계약 검사는 따로 두지 않는다.** 매일 배치가 그 역할을 한다.

## 7. 범위 밖

- 팝업 데이터.
- 예매 순위, 장르 칩, 가격 필터.
- 공연 전용 화면이나 그룹.
- 회차별 시간 파싱(`dtguidance`는 원문 그대로).
- 아마추어·주민 공연을 정확히 가려내는 분류. 이번엔 시설특성 신호만 쓴다.

## 8. 실패로 보는 것 (지금 기술적으로 동작해도)

- 선반이 대학로 공연으로만 채워진다(위치가 대학로가 아닌데도).
- 공연이 목록을 덮어 기존 행사가 안 보인다. 공연은 하루 약 300건이라 "전체" 목록 비중이 커진다 — 화면에서 확인한다.
- 같은 공연이 서울시 항목과 KOPIS 항목으로 두 번 나온다.
- 차단이나 키 만료로 공연이 조용히 0건이 된다.

## 9. 계획에서 정할 것

- 중복 판정 규칙(4장).
- 주간 큐레이션 단계(`curate`, LLM 제공자, `data/curated/`)를 지울지 남길지. 선반은 더 이상 읽지 않는다.
- 위치 없을 때 5개 생활권 중 3개를 고르는 방법(5장).
- 가산점 초깃값.
- 포스터 https 여부 확인과, 안 되면 처리(대체 이미지 등).
- 초기 적재를 배치에서 할지, 로컬에서 한 번 돌려 캐시를 커밋할지.
