# 디자인 플레이그라운드 — 설계

2026-11-04. 브레인스토밍 합의(사용자와 대화). 이 문서는 그 결과를 적은 것이다.

## 1. 왜

디자인 시스템의 근거는 코드다(`src/styles/theme.css`, `src/styles/foundation.css`, `src/components/`).
설명은 DESIGN.md에 있다. 하지만 한 화면에서 전체를 보는 곳이 없다.

한 번 claude.ai 디자인 시스템 페이지로 만들어 봤다. 구성은 좋았지만, 그 페이지는 AI가 코드를 읽고
해석해서 손으로 옮긴 결과물이다. 코드가 바뀌면 다시 사람(또는 AI)이 옮겨야 하고, 옮기는 과정에서
어긋날 수 있다.

**요구.** 코드가 SSOT이고, 플레이그라운드는 코드가 바뀐 뒤 빌드가 결정적으로 만들어 내는 결과물이어야 한다.

## 2. 쓰는 순간

사용자가 든 장면 둘:

1. **디자인 시스템을 개선할 때.** 전체를 훑으며 빈 토큰, 너무 가까운 값, 다크에서 어색한 컴포넌트를 찾는다.
2. **작업 중 옆에 띄워 두고 에이전트에게 요청할 때.** 페이지에 보이는 이름을 보통 손으로 옮겨 적고, 길면 복사한다.

## 3. 목표

- 앱 안의 `/playground` 경로. 앱 빌드에 포함돼 GitHub Pages로 함께 배포된다(사용자 결정).
- 홈·탐색 화면에서는 링크하지 않는다. 주소로만 연다. 검색 엔진 색인은 막는다(`noindex`). (내 결정)
- 토큰 표는 빌드할 때 `theme.css`·`foundation.css` 원문을 읽어 만든다. 손으로 옮긴 표가 없다.
- 컴포넌트는 실제 코드를 import해 렌더링한다. 손 번역이 없다.
- 페이지에 보이는 이름은 코드에 그대로 쓰는 이름이다. 토큰 이름과 Tailwind 클래스(`text-ink-subtle`, `gap-100`, `rounded-full`)를 함께 보인다.
- 컴포넌트 견본마다 호출 예시를 붙이고, 긴 호출 예시에만 복사 버튼을 둔다(내 결정 — 사용자는 보통 손으로 옮기고 길면 복사).
- 라이트와 다크를 나란히 보인다.
- `ui.tsx`·`cards.tsx`에 새 export가 생겼는데 플레이그라운드에 없으면 테스트가 실패한다.

## 4. 비목표

- 페이지 안에서 토큰 편집.
- 디자인 개선 제안 자동 생성.
- claude.ai 디자인 시스템 페이지와의 동기화. 그 페이지는 그대로 둔다(지울지는 사용자 몫).
- 브랜드북 글 복제. DESIGN.md·PRODUCT.md가 SSOT라 링크만 건다.
- 홈·탐색 화면 단위 조각(`HomeControls`, `BrowseControls`, `TimelineSection` 등).

## 5. 페이지 구성

claude.ai 페이지에서 사용자가 좋다고 한 순서를 따른다.

1. **머리.** "디자인 시스템" 제목, 빌드 기준 커밋(짧은 sha), DESIGN.md·PRODUCT.md로 가는 GitHub 링크.
2. **색.**
   - 스케일 6개(accent, neutral, error, warning, success, info) × 11 stop 프리미티브.
   - 스케일별 역할 7개(`subtle-bg`, `hover-bg`, `border`, `solid`, `on-solid`, `text`, `text-strong`). 라이트·다크 값과 가리키는 프리미티브.
   - 표면·잉크 4개(`surface`, `ink`, `ink-muted`, `ink-subtle`).
   - 각 칸에 토큰 이름, 대표 클래스, 값. 글자 역할에는 바탕과의 대비 값을 페이지가 직접 계산해 보인다. 쌍은 DESIGN.md "대비" 장의 검사 쌍(text·text-strong·on-solid·ink 계열)이다.
3. **글자.** 역할 7개. 견본 문장, 크기/줄 높이/굵기, 클래스(`text-caption`).
4. **간격.** 원시 스케일 15개와 레이아웃 토큰 3개(`gutter`, `section`, `page`). 막대 견본과 값, 클래스 예(`gap-100`). 레이아웃 토큰은 폭별 값을 함께 보인다(미디어 쿼리 원문에서).
5. **모서리.** 4개. 견본과 클래스(`rounded-100`).
6. **컴포넌트.** `ui.tsx`(button, chip, Chip, ChipSelect, Callout), `cards.tsx`(EventPosterCard, ListRow), ItemImage, OpenNowBadge, ThemeToggle. 각 견본은 라이트·다크 두 칸에 같은 것을 그리고, 아래에 호출 예시.

## 6. 결정성

- **토큰.** 플레이그라운드는 CSS 원문을 빌드 입력으로 받는다(Vite `?raw` import). 파서는 순수 함수이고 테스트가 붙는다. 표에 나오는 이름·값·순서는 원문에서만 나온다.
- **카드 견본 데이터.** 플레이그라운드 파일 안의 고정 예시. 배치 데이터(`data/`)를 읽지 않는다.
- **이미지.** 외부 이미지를 쓰지 않는다. `ItemImage`는 src 없이 그려 카테고리 폴백 색이 깔리게 한다 — 그 8색이 시스템 밖 값이라는 사실(DESIGN.md "아직 안 정한 것")도 그대로 드러난다.
- **시간 의존.** `OpenNowBadge`는 브라우저 시각으로 판정한다. 견본은 00:00~24:00 영업시간을 줘서 언제 열어도 보이게 한다. 카드의 "남은 기간"은 견본 날짜를 고정 today 기준으로 준다.
- **배포.** 다른 화면과 같은 정적 프리렌더. `vite.config.ts`의 `pages`에 `/playground`를 넣는다(링크가 없어 크롤로는 못 줍는다).

## 7. 라이트·다크 나란히

다크 값은 `.dark` 선택자에서 역할 변수만 다시 선언한다. 그래서 다크 칸은 `class="dark"` 래퍼로 감싸면 된다.

반대로 페이지가 다크일 때 라이트 칸은 `.dark`를 되돌릴 선택자가 없다. 라이트 칸은 파싱한 `@theme` 블록의 역할 값을
인라인 스타일 변수로 다시 선언해 감싼다. 이 값도 원문에서 나오므로 손으로 옮긴 값이 없다.

## 8. 누락 테스트

`ui.tsx`·`cards.tsx`·`ItemImage.tsx`·`OpenNowBadge.tsx`·`ThemeToggle.tsx`의 export 이름 집합이
플레이그라운드가 견본을 가진 이름 집합과 같아야 한다. 새 컴포넌트를 추가하고 견본을 안 만들면 테스트가 실패한다.

## 9. 빌더에게 남긴 것

- 파서 모듈 위치와 반환 타입 모양.
- 페이지 안 레이아웃(그리드 열 수, 견본 크기). 디자인 시스템 토큰과 `ui.tsx` 컴포넌트만 쓴다. 새 색을 만들지 않는다.
- 커밋 sha를 빌드에 넣는 방법(`define` 등).
- 복사 버튼을 붙일 "긴" 호출 예시의 기준.
