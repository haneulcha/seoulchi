# 오늘 중심 홈 설계 (2026-10-26)

홈을 "이번 주 12개"에서 **오늘·내일·이번 주말에 갈 수 있는 행사 전체**로 바꾼다.
같이 바꾸는 것 둘: PRODUCT.md의 "망라는 팔지 않는다" 원칙과, 행사 종류 기준의 카테고리.

이 문서는 `2026-08-13-seoul-events-webapp-design.md`(웹앱 1차)와
`2026-08-31-browse-mode-design.md`(탐색)를 대체하지 않고 홈 부분만 고쳐 쓴다.

## 1. 왜

PRODUCT.md는 이미 "무게는 오늘에 둡니다"(2026-10-26)라고 정했다. 기준 장면은 휴일 아침
"오늘 뭐 재밌는 거 없나" 하며 여는 순간이다. 그런데 홈은 아직 이번 주 12개를 고른 화면이고,
그 12칸은 "망라는 팔지 않는다"와 "선별은 유지하되 자리를 남은 것으로 채우지 않는다"라는
두 원칙이 만든 모양이다.

사용자 판단: 이 두 원칙이 **제품을 답답하게 만든다.** 오늘 갈 수 있는 것을 다 보고 싶은 순간을 막는다.
그래서 내려놓고, 줄이는 일은 필터가 맡는다.

홈에서 사용자가 찾는 것(사용자 답): **지역별로 보기, 내 주변에서 찾기, 행사의 성격.**
참고한 것은 walkerplus의 오늘 화면이다. 날짜 탭(오늘·내일·주말), 지역 선택, 목적 선택(먹기·놀기·보고 배우기) 아래에
전체 목록이 이어진다. "내 주변"은 거기 없고 우리가 좌표로 할 수 있는 것이다.

## 2. 결정

| 항목 | 결정 | 누가 |
|---|---|---|
| 망라 | 허용. 그날 갈 수 있는 것 전부를 보여주고 필터로 좁힌다 | 사용자 |
| 카테고리 | 행사 종류 6그룹 → **목적 4그룹** ("가서 뭘 하나") | 사용자 (그룹 구성은 3장, 초안을 사용자가 승인) |
| 홈 필터 | 지역 · 내 주변 · 목적 | 사용자 |
| 날짜 | 오늘 · 내일 · 이번 주말 탭으로 넘겨 본다 | 사용자 |
| 추천 | 12개는 빼고, 맨 위에 **추천 선반**만 남긴다 | 사용자 |
| 추천 선반과 필터 | 필터·날짜 탭과 무관하게 늘 같은 자리 | 사용자("고려하지 않아도 돼") → 고정으로 해석 |
| 장소 | 홈 목록에 섞지 않는다. 행사와 구분하고, 장소는 **행사에서 연계해 들를 곳**으로 쓴다 | 사용자 (2026-10-27, "섞는다"를 뒤집음) |
| 탐색 탭 | **남긴다.** 먼 날짜와 장소 전체를 맡는다(범위는 7장) | 사용자 |
| 목록 순서 | 곧 끝나는 것 먼저 | 제안, 사용자 이의 없음 |

## 3. 목적 그룹

walkerplus의 "먹기"는 뺀다. 서울 공공 데이터에 음식 행사가 거의 없다(추정, 구현 전 원시 분류값으로 확인).

| 그룹 | 지금 그룹에서 | 비고 |
|---|---|---|
| 보러 가기 | 전시, 공연 | 박물관·미술관·영화 포함 |
| 해보러 가기 | 체험·배움 | |
| 걸으러 가기 | 공원·자연, 역사·명소 | |
| 놀러 가기 | 축제 | |
| 기타 | 기타 | 칩에는 없고 전체에는 있다(지금과 같다) |

매핑은 지금처럼 **원시값 → 그룹** 표(`src/lib/category.ts`의 `GROUP_BY_RAW`)로 한다. 위 표는 출발점이고,
원시값 단위로 옮길 수 있다. 제 판단으로 `테마공원`·`레저스포츠시설`은 걸으러가 아니라 **놀러 가기**로 보낸다
(Claude 결정, 사용자 확인 전).

탐색 탭의 칩도 같은 4그룹으로 바꾼다. 화면마다 분류가 다르면 안 된다(Claude 결정).

`group`은 배치가 데이터 파일에 써 넣는 값이다. 읽을 때 다시 매핑하지 않고, 그룹 enum과 매핑 표를 바꾼 뒤
데이터를 다시 만든다. 화면과 데이터의 그룹이 늘 하나다(Claude 결정).

## 4. 홈 화면

위에서 아래로:

1. **추천 선반.** 지금의 포스터 선반 그대로, 3개, 배치가 쓴 한 줄 이유와 함께.
   이번 주말까지 하루도 갈 수 없는 추천을 먼저 빼고, 남은 것에서 앞의 3개를 쓴다(Claude 결정).
   추천은 지금처럼 행사만이다. 1~2개만 남아도 같은 선반 모양이고, 0개면 선반을 접는다.
   추천에 오른 것은 아래 목록에서 다시 보이지 않는다.
2. **날짜 탭.** 오늘 · 내일 · 이번 주말. 기본은 오늘.
3. **필터.** 지역(자치구 선택) · 내 주변(토글) · 목적(칩 3개). 날짜 탭을 바꿔도 유지된다.
   홈의 목적 칩은 보러 가기 · 해보러 가기 · 놀러 가기다. 걸으러 가기(공원·자연, 역사·명소)는 실측상 100% 장소라
   행사만 있는 홈에서는 늘 비어서 뺀다. 탐색 탭과 장소 연계에서만 쓴다(사용자 결정, 2026-10-27).
4. **그날의 목록.** 그날 갈 수 있는 행사의 목록 행(`ListRow`). 개수를 보여준다.

빠지는 것: "이번 주에 더 있는 것" 9개, "언제 가도 좋은 곳" 6개 그리드.

### 그날 갈 수 있다의 뜻

- **행사.** `startDate <= 그날 <= endDate`. 이번 주말 탭은 그 기간과 하루라도 겹치면.
- **쉬는 요일.** 기간 안이어도 그날 요일에 쉬는 행사는 뺀다(사용자 결정, 2026-10-28). 요일은 행사의 시간 문구
  (`time`, 예: "화-일 10:00~18:00 / 월요일 휴관", "매주 (토) 14:00~17:00")에서 읽는다.
  읽지 못하면 남긴다. 장소의 영업시간 미상과 같은 태도다. 모르는 것을 쉰다고 말하지 않는다.
  이번 주말 탭은 토·일 중 하루라도 여는 행사를 남긴다. 공휴일 휴관은 다루지 않는다.
  2026-10-28 시안 실측: 오늘 진행 중이면서 `time`이 있는 229건 중 130건에서 요일을 읽었고 114건이 특정 요일만 연다.
  `parseHours`(장소용)는 쓸 수 없다. "X요일"을 전부 휴무로 읽어서 "매주 토요일"을 토요일 휴무로 만든다.
- **이번 주말.** 다가오는 토·일. 오늘이 토요일이면 토·일, 일요일이면 일요일 하루.

### 순서

- 기본은 곧 끝나는 순(`endDate` 오름차순). ("같은 날 끝나면 사진 있는 것 먼저"는 2026-10-27 실측으로 뺐다. 오늘 행사 262건 전부 사진이 있다.)
- 내 주변을 켜면 거리순으로 바뀐다. 탐색과 같다.

### 내 주변

탐색과 같다. 토글을 눌렀을 때만 위치 권한을 묻고, 거절하면 이유를 보이고 지역으로 좁히라고 안내한다.
첫 화면에서 권한을 조르지 않는다(Claude 결정).

## 5. 바꿀 문서

- **PRODUCT.md.** Purpose의 "추천은 이번 주에 갈 만한 것을 12개로 추리고",
  "무게는 오늘에" 단락의 마지막 문장("홈의 이번 주 12개 구성은 아직 그대로"),
  Positioning 전체(두 경로의 역할과 "망라 자체는 여전히 팔지 않습니다" 단락),
  디자인 원칙 "선별은 유지하되 자리를 남은 것으로 채우지 않는다"를 고쳐 쓴다.
  새 입장: 그날 갈 수 있는 것은 다 보여준다. 줄이는 건 필터와 순서가 하고, 추천 선반은 출발점 몇 개를 건넨다.
- **탐색 설계(2026-08-31).** 카테고리 6그룹 → 4그룹, 탐색의 범위 변화를 메모로 남긴다.

## 6. 미결

- 홈 데이터 경로. 지금 홈은 빌드 때 오늘을 정하는 프리렌더다. 날짜 탭과 필터를 쓰려면
  목록은 탐색처럼 `index.json`을 클라이언트에서 받아 브라우저의 오늘로 계산하는 쪽이 자연스럽다.
  추천 선반은 지금처럼 프리렌더로 둘 수 있다. 빌더 판단.

## 7. 탐색 탭

범위는 지금처럼 오늘부터 8주로 둔다. 홈과 앞쪽 며칠이 겹치지만, 탐색의 시간 축 묶음을 고치는 비용에 비해
얻는 게 없다(Claude 결정). 바뀌는 건 카테고리 칩뿐이다.

## 8. 장소 연계 (별도 설계)

장소는 홈 목록에 서지 않고, 행사에서 이어 들를 곳으로 나온다(사용자 결정). 예를 들면 행사 상세에서
"근처에 들를 곳"을 보여주는 식이다(Claude 추측). 어디에 어떻게 붙일지는 이 문서 범위 밖이고 따로 설계한다.
그 전까지 장소 전체 목록은 탐색 탭에 그대로 있다.
